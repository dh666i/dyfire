## 留待审查

| 项目 | 实际影响及证据 | 建议与保留原因 |
| --- | --- | --- |
| PostgreSQL 并发初始化 | `spark_console/db.py` 的 `create_all`、检查列后 ALTER、WorkerLock 先查后插没有统一串行化；首次空库多服务同时启动存在竞态。 | 切换 PostgreSQL 前，以同一连接的 advisory lock 串行初始化、使用冲突安全插入并做真实多进程验收。本机未配置 PostgreSQL，不把此问题当作当前 SQLite 线上故障。 |
| 数据库兼容回滚范围 | SQLite 启动不拒绝比程序更新的迁移版本；更新器又允许同一数据兼容协议回退旧镜像并保留新库。 | 先定义可读/可写兼容范围，再增加保护。不能简单禁止所有更高迁移版本，否则加表、加索引后原本可行的回滚也会被阻断。参见 `spark_console/db.py`、`deploy/updater.py`。 |
| 账号恢复的长事务 | `spark_console/services/account_health.py::skip_missed` 及 `recovered` 按任务逐条读取/写入，没有独立的分批完成机制；大量积压任务可能延迟复核完成并占用 SQLite 写锁。 | 设计持久化恢复批次和进度，再分批推进；不能只加 LIMIT，否则剩余任务可能被普通调度器误补发。需要容量场景验收。 |
| 历史或导入付款摘要 | `spark_console/db.py` 旧字段回填使用随机值/MD5，`services/operations.py` 用请求字段 SHA256；此类记录原请求重试会冲突。 | 付款模型、服务、摘要迁移同时首次加入 `018db8c6`，未证实正式版本存在无摘要付款。先只读盘点导入/历史数据，再显式修复；不放宽所有摘要不匹配，避免破坏幂等保护。 |
| 人工修改或导入后的孤立运行记录 | `scheduler.py::_reclaim_expired_run` 内连接账号且要求 dispatch_key；已解绑或分片键为空的异常历史运行可能长期停在 running。 | 正常解绑接口已有 running 拦截，数据库初始化也回填分片键；先盘点是否实际存在，再做有界、绝不重发的记录收敛。保留已提交待核实的语义。 |
| 本地未跟踪旧部署资料 | 根目录 `*-v0.2.75.*`、旧状态报告、`deploy/git_web_updater_improved.py` 等仍使用旧服务器/路径/可变镜像标签，旧更新器还会正则改 Compose。当前生产更新链不引用这些文件。 | 本轮不删除用户未跟踪文件；建议确认后归档或移除，避免误执行。现有 `.claude` 配置含明文连接凭据；若仍有效应轮换，忽略 Git 不能替代轮换。 |
| 旧命令行链路及依赖 | `core/tasks.py` 中 `runTasks/do_user_task/scroll_and_select_user` 未找到当前受控代码的外部调用；仍通过模块顶层导入旧消息生成、OpenAI 等链路，`utils` 还含旧节日文案/剪贴板配置工具。 | 先明确是否还需外部脚本兼容，再一起移除旧入口及其专属依赖、重建运行时镜像锁。不要仅删除依赖，否则现有顶层导入会失败。 |
| CSS 与页面模块继续拆分 | 构建时主 CSS 约 513 kB（gzip 137 kB），主入口 JS 约 436 kB（gzip 142 kB），另有独立 vendor/管理页；多层 CSS 覆盖和大 JSX 文件增加维护难度。 | 按实际加载/覆盖证据分离页面样式和模块，先测首屏再优化；不靠关键词批量删 CSS 或重新设计用户喜欢的界面。当前重复完整规则检查为 0。 |
| GHCR 候选与缓存保留策略 | 工作流不断产生提交候选、运行时维护标签，仓库没有自动清理策略；镜像层可复用，但远端历史对象仍会积累。 | 制定保留最近正式版本、实际部署/回滚摘要、运行层和缓存引用的规则，先只读盘点再清理。不能直接按标签年龄删除，可能误伤可回滚镜像。 |
