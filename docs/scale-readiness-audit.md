# Dyfire 全站专业化审计与扩容路线图

审计基线：`main` 分支，版本 `0.3.8`。本文区分已经在代码中完成的改进、当前仍存在的限制，以及达到大规模商用前必须验收的工作。它不是容量承诺；在完成压测和故障演练前，不应对外宣称系统支持几十万用户。

## 已完成的近期改进

- 工作台和管理后台的执行记录、今日统计、账号健康状态、任务身份查询已减少明显的全量读取和 N+1 查询。
- 增加了调度、执行记录、会话、订阅和审计查询使用的复合索引，并提供 SQLite v10 迁移。
- SQLite v11 已加入账号 dispatch key；v12 为 retention 的终态时间查询增加复合索引，v13 为账号队列增加复合索引，PostgreSQL 新库由模型元数据创建同等索引。
- SQLite v15 为审计事件增加可空的 `request_id`、`client_ip`、`outcome` 和 `error_code` 字段，并建立请求索引。HTTP 请求会自动把请求 ID 和可信代理解析后的客户端地址写入审计事件；历史记录保持为空，不会被猜测性回填。PostgreSQL 启动时执行同样的加法迁移，字段缺失会在服务启动前被发现。
- SQLite v13 为账号健康、过期操作和目录队列增加复合索引；索引改进不等同于生产 worker 容量已经通过验收。
- `psycopg` 已纳入容器依赖，配置 `postgresql+psycopg://...` 可启动 PostgreSQL 新库；现有 SQLite 数据不会自动迁移，正式切换前必须执行离线迁移和回放校验。
- API 默认返回 `Cache-Control: no-store`，CSRF 非字符串输入返回 403，登录失败限流有内存上限。
- 普通用户与管理员角色变更会撤销目标用户现有会话，并保留最后一名管理员保护和审计事件。
- 管理员初始化响应不再携带全部明文兑换码；兑换码页面使用独立接口、搜索和分页加载。
- 应用层增加可配置的请求体上限 `SPARK_MAX_REQUEST_BYTES`，默认 2 MiB。反向代理仍必须设置相同或更严格的限制。
- 转发头由应用层按 `SPARK_TRUSTED_PROXY_CIDRS` 严格限制：未配置时忽略 `X-Forwarded-For/Proto`；只有直接对端属于配置的 IP/CIDR 时才解析最近的客户端地址和 HTTPS scheme。HSTS 可通过 `SPARK_HSTS_MAX_AGE_SECONDS` 与 `SPARK_HSTS_INCLUDE_SUBDOMAINS` 配置。
- HTTP 响应统一带 `X-Request-ID`；JSON API 错误追加 `request_id` 和稳定的 `error_code`，便于用户反馈、日志检索和告警关联。
- 会话令牌校验已改为绑定 `session.key` 的 HMAC；轮换该密钥会使现有浏览器会话失效，数据库泄露也不能单独离线验证令牌。
- 管理员提供当前浏览器会话范围的 15 分钟密码 step-up 接口 `/api/auth/elevate`，失败尝试审计并限流；高风险后台动作仍需逐项接入并完成 UI 引导后再强制启用。
- 管理员 TOTP 已提供可选 enrollment 准备层：`/api/auth/mfa/totp`、`setup`、`confirm` 和 `disable`。密钥以 AES-GCM 密文保存（使用部署的 `session.key`，轮换该密钥会同时使网页会话和 TOTP 密文失效，需重新 enrollment），setup 只返回一次 `otpauth://` URI，确认记录 RFC 6238 时间步并拒绝重放；默认不会改变登录、现有 WebSession、密码 step-up、抖音 Cookie 或任务执行。启用 MFA 强制策略前，必须补管理界面、恢复码/丢失设备流程、跨进程限流和独立回归演练，并单独审阅发布开关。
- `SPARK_REQUIRE_ADMIN_STEP_UP=true` 时，后台写接口统一要求 step-up；前端会在 428 响应后请求密码并重试原操作。生产部署该开关前应确认管理员已使用包含验证面板的前端版本。
- `queue-preflight` CLI 会只读检查数据库领取表、字段和 worker 分片配置；在显式传入 `--probe-stream` 时，才对 Redis 使用随机临时 Stream 做发布、消费、确认和清理。它不接管生产任务，也不改变默认数据库领取路径，可作为 PostgreSQL/Redis 分阶段切换前的运维门禁。
- 已提供默认 dry-run 的 retention CLI，可分批清理终态执行、登录会话、邮件和审计记录，并保护活跃/待核实数据。
- `deploy/recovery_drill.py` 提供隔离恢复演练：源备份只读，全新副本执行表集合、内容指纹、SQLite 完整性、外键、schema migration 和可选 Cookie 解密校验；默认删除临时副本，失败不会留下未验证数据库。
- 移动端时间输入已设置单列布局、`min-width: 0` 和 `box-sizing`，应在真机和常见浏览器再次核验。

## P0：上线前必须解决

### 数据与执行架构

当前生产仍是 SQLite 单文件、单个全局 `WorkerLock`、单机浏览器执行和进程内限流。它适合小规模部署，不适合数十万用户或高峰期任务扇出。

目标架构：

1. PostgreSQL 承担事务数据；使用行级锁和 `FOR UPDATE SKIP LOCKED` 领取任务。
2. Redis 适配层已提供分布式限流、短期状态、幂等和有界队列所需的原子原语，并在隔离 CI 服务中验证。新增 Redis Streams 消费组原语保留未确认消息、支持跨消费者回收 idle pending 消息，并明确采用至少一次投递；当前仍未接入生产发送链路。正式接入前必须完成 AOF/RDB 持久化策略、故障降级、业务幂等键、重复投递和恢复演练。
3. 使用持久化任务队列，将扫描、登录复核和发送任务从 Web 请求中移出。
4. 按抖音账号分片执行，并为每个账号设置并发信号量，移除全局 WorkerLock 串行瓶颈。当前版本已提供可渐进启用的 `SPARK_WORKER_SHARD` / `SPARK_WORKER_SHARDS`：账号按稳定 SHA-256 key 分配到分片，任务新领、过期回收和健康恢复均带分片条件；仍需在 PostgreSQL/Redis 队列环境完成压测后再提高分片数量。
5. 截图、二维码帧和大对象放入对象存储，数据库只保存元数据和生命周期信息。

迁移验收：双写或回放测试通过；断电、重复投递、队列积压和 worker 重启不产生重复发送；任务领取、重试、取消都有幂等键。Redis Streams 只能证明消息交付，不等同于发送幂等：业务消费者必须在发送前后使用持久化幂等记录，处理 `stream_reclaim` 带来的至少一次重投。

### 管理员安全

- 将二元 `admin/user` 升级为 `super_admin`、`ops_admin`、`support_admin`、`sales_admin` 和 `user`，按资源和客户归属检查权限。
- 所有管理员启用 MFA 或 Passkey；角色变更、密码重置、兑换码生成与查看、SMTP、部署更新要求 step-up 认证。
- 兑换码使用检索 hash 加密密文存储；后台默认只显示脱敏标识，明确点击单条查看时才解密，并记录查看审计。
- 配置可信反向代理 IP 链。只有来自可信代理的 `X-Forwarded-For/Proto` 才能影响客户端 IP 和 HTTPS 判断。
- 反向代理和应用同时设置请求大小、连接超时、上游读取超时、严格 HSTS、CSP、COOP、CORP、Secure/HttpOnly/SameSite Cookie。

### 灾备与发布

- 加密的 3-2-1 备份，数据库、密钥和对象存储分开保存；定义 RPO/RTO。
- 每月执行恢复演练，验证能恢复到独立环境并完成登录、任务创建和安全发送检查。
- 发布采用 canary 或灰度；健康检查失败自动回滚镜像，但不自动回滚业务数据库以免重复发送。

## P1：规模化前完成

- `/api/app/bootstrap` 已将账号和任务首屏读取限制为 100 条，并通过 `/api/app/tasks` 分页加载后续任务；管理端已将任务分组、订阅、审计、邮件和兑换码改为按页面加载。后续可将偏移分页继续升级为 keyset/cursor 分页。
- 用户、任务、执行记录、审计、邮件和账号告警设置保留期与归档策略，避免主表无限增长。
- 搜索从 `%keyword%` 模糊匹配升级为前缀、全文或 trigram 索引；统计使用汇总表或事件驱动计数。
- 增加 `tenant_id`、客户归属、邀请、订单、支付、退款、佣金账本、结算周期和退款追回模型。管理员备注只能作为展示字段，不能承担下线关系。
- 所有写接口支持幂等键、统一错误码和 trace ID；敏感操作记录操作者、目标、结果和请求 ID。
- 管理后台提供队列延迟、失败率、账号验证率、发送成功率、磁盘/WAL、备份新鲜度和登录异常的告警，并定义责任人和升级路径。

## P2：体验与运营

- 新用户引导改为服务端状态，按“绑定账号、同步好友、创建任务、首次成功发送、订阅到期”逐步完成，而不是只依赖浏览器 localStorage。
- 订阅页清晰展示 9.9/15/20 元套餐、任务上限、账号上限、有效期起算规则和联系客服入口；订单和兑换码展示统一使用计划快照。
- 移动端用真实 iOS Safari、Android Chrome 检查时间控件、二维码、底部导航、抽屉、键盘和窄屏横向溢出。
- 前端为加载、空数据、权限不足、过期会话、网络中断、重复提交和异步任务超时提供明确状态。

## 压测基线

### 当前已验证的 500 客户数据基线

`tests/console/test_scale_baseline.py` 使用临时 SQLite 数据库构造 500 名普通客户、1 名管理员、500 个抖音账号、2500 个任务和 75000 条执行记录，通过 FastAPI `TestClient` 的分页、顺序请求和 12 线程只读请求验证 API。该测试验证：

- 管理员用户列表和执行记录分页有边界；首页、后续页和单客户筛选的账号查询保持批量读取。
- 用户工作台的 SQL 查询次数在 1 个任务与 9 个任务的数据集下相同，避免逐任务读取身份和健康状态。
- 普通用户不能查看或修改其他用户的账号、任务，也不能访问管理员接口；管理员客户工作台按客户隔离。
- API 读取没有数据库写操作；全部账号的 Cookie 密文、nonce、版本、验证状态，以及任务目标和发送计划保持原值。
- 重复执行规模相关的 SQLite schema 升级不会改变已有登录密文和任务，原密钥仍可解密全部模拟 Cookie。
- 36 个并发只读会话各请求工作台、执行记录和 bootstrap，响应全部成功、客户数据隔离保持、数据库没有写入。

### 当前已验证的 PostgreSQL 隔离基线

GitHub Actions 的 PostgreSQL 16 service 会创建随机隔离 schema，装载同等的 500 名客户、500 个账号、2500 个任务和 75000 条执行记录，并为每名客户创建独立会话。测试至少覆盖 500 个客户工作台请求，再并发执行管理员分页和执行记录读取；记录 p50/p95、失败率、连接池耗尽情况，并验证所有 Cookie 密文、任务目标和身份读取后不变。schema 在 teardown 时删除，不接触生产数据库。

最近一次 CI 实测（GitHub Actions PostgreSQL 16 service，2026-10-01）：装载耗时 `8.629s`，共 `540` 个只读请求、`12` 个并发 worker，p50 `0.353s`、p95 `0.515s`、失败率 `0`。同一隔离 schema 的任务领取演练使用 `120` 个到期任务和 `12` 个 worker，`120` 次唯一领取、重复 `0`、失败 `0`，p50 `0.096s`、p95 `0.235s`。这些数字用于回归比较，不是目标服务器 SLA；依赖的硬件、网络、连接池和数据分布不同，必须重新测量。

该基线证明 PostgreSQL 连接池和 API 读路径在 CI 的临时服务容器中能处理代表性数据，不等于成都服务器的持续发送容量、真实抖音浏览器容量或 SLA。Redis 适配层已在隔离 CI service 中验证，但尚未切入生产发送路径；正式扩容前仍需在目标资源上启用并验证 Redis、持久队列、真实任务峰值和 worker 故障恢复演练。

这是数据规模与接口行为回归基线，不是 500 人同时在线或生产发送能力的容量证明。并发请求只覆盖本地 SQLite 的只读 API，不代表生产 PostgreSQL、Redis、队列或真实抖音浏览器容量。模拟 Cookie 不连接抖音，测试没有启动真实浏览器、发送消息、经过公网代理，也没有测量持续并发下的 p95/p99、CPU/内存峰值和峰时队列延迟。测试打印的耗时是当前开发机单次执行结果，不应用于生产 SLA 或并发承诺。

`tests/console/test_postgres_scale_baseline.py` 在 CI 的 PostgreSQL 16 service 中执行同等数据规模。它为每次运行创建随机 schema，使用合成的加密 Cookie 和 HMAC 会话，为 500 个客户各发送一次工作台读取，再以 12 个线程并发执行用户执行记录、管理员用户/执行记录/订阅/任务分组读取；测试输出 p50、p95 和失败率，并要求所有响应成功、读取期间无 INSERT/UPDATE/DELETE、全部账号 Cookie 字段和任务身份/发送计划保持一致。测试结束后删除随机 schema，未配置 `TEST_POSTGRES_URL` 时跳过。这个基线只说明当前 CI service 上的 API 回归表现，不能推导生产服务器的 SLA、真实抖音发送吞吐或可支持的在线人数；应结合实际资源持续压测并记录 CPU、内存、连接池、锁等待和队列延迟。

“先达到几百客户级别”的下一步验收，应在隔离环境按实际服务器资源和任务时间分布测量持续 API 并发与执行队列，覆盖绑定/复核/发送的竞争、单账号串行、过期领取和 worker 重启。真实账号验证只使用明确指定的测试账号和收件人，已绑定的生产账号、登录密钥与现有任务不作为压测数据。未通过这些验收前，只能表述为“500 客户数据基线已通过”。

### 大规模架构验收

在 PostgreSQL、Redis、队列和分片执行器上线后，至少验证：

- 100,000 用户、1,000,000 任务、10,000,000 执行记录的查询延迟和存储增长。
- 登录、好友同步、任务创建、订阅兑换同时高峰的 p95/p99 延迟。
- 任务高峰扇出、单账号串行约束、队列积压、重复消息保护和 worker 故障转移。
- 数据库故障、Redis 故障、对象存储暂时不可用、反向代理重启和发布回滚。

只有压测、恢复演练和安全评审均通过后，才适合扩大公开推广和 reseller 网络。
